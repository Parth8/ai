How to use this

In order, mostly.

Each phase assumes the one before it. Skipping to agents because they're fashionable is how people end up able to use AI but unable to explain it.

Watch less, build more.

After every phase, make one small thing before moving on. A half-finished project that touches real data teaches more than three completed courses.

Free first.

The best AI education happens to be free: Karpathy, 3Blue1Brown, StatQuest, DeepLearning.AI short courses, Hugging Face. Paid options are marked and optional.

00
phase zero

The Builder's Toolkit

Before machine learning: the working skills every later phase silently assumes. Python you can actually modify, Git you actually use, terminals, HTTP, and the craft of reading documentation. Skippable only if you already do all of it weekly.

1–2 weeks · ~10 hours, then reinforced forever

When this is done: you can clone a repo, create a branch, run a Python project in a virtual environment, call an HTTP API with an auth key, keep secrets out of your code, work in a notebook, and navigate any library's documentation from quickstart to API reference without panic.

Concepts to own

Python: read → modify → compose
You don't need to be a software engineer. You need to read a script, change what it does, and glue libraries together: functions, dicts and lists, imports, pip/uv, virtual environments, and reading a traceback without fear. Every AI tutorial on earth assumes exactly this level.
Git & GitHub
Clone, branch, commit, push, pull request, resolve a merge conflict - the six moves that cover 95% of real usage. Version control is also how you'll read other people's AI projects, ship your own, and (as a "builder PM") review and merge actual code.
The terminal
Navigate directories, run scripts, set environment variables, chain commands, read logs. Every model server, training script, and deployment tool is terminal-first; the GUI versions always lag.
HTTP, JSON & API anatomy
Request method, URL, headers, auth token, body; response status code and JSON payload. Every model API in this curriculum is exactly this shape. Learn to make one call with curl and one with Python's requests, and the rest is repetition.
Secrets hygiene
API keys live in environment variables or .env files, never in code, never in Git. One leaked key on GitHub gets auto-scraped within minutes and billed to you. This habit is non-negotiable from day one.
Notebooks: Jupyter & Colab
Cell-by-cell execution with output inline - the native format of ML experimentation and of most course material. Colab adds a free GPU in the browser. Know when notebooks help (exploration) and when they hurt (anything you'll run twice).
How to read documentation
Quickstart first, concepts second, API reference only on demand - and changelog when things break. Docs literacy is the actual superpower behind "picks things up fast," and it's a learnable skill, not a personality trait.

01
phase one

Machine Learning Foundations

Everything before LLMs. What a model actually is, what "learning" mechanically means, and the statistical intuition the whole field is built on. Skipping this is why most AI knowledge collapses under one hard question.

1–2 weeks · ~12 hours of material

When this is done: you can explain - without buzzwords - what a model is (a shape with trainable blanks), what training does (guess, measure error, nudge, repeat), why models overfit and generalize, how to read an evaluation metric, and where classical ML still beats deep learning in production.

Concepts to own

What a model actually is
A deliberately simplified stand-in for a real-world process. In ML: an architecture (the shape of a formula, with blanks) plus parameters (the numbers filling those blanks). "GPT has 1.8T parameters" just means 1.8 trillion filled-in blanks. Everything else in this curriculum lives inside this frame.
Training = guess, measure, nudge, repeat
A loss function scores how wrong a prediction was; gradient descent computes which direction to nudge every parameter to be slightly less wrong; backpropagation is the trick that computes those nudges efficiently. Millions of tiny corrections, no rules ever written by hand.
Supervised, unsupervised, reinforcement
Learn from labeled examples (spam / not spam), find structure without labels (clustering, embeddings), or learn from delayed rewards (game-playing, RLHF later on). These three words carve up the entire field - know which one any technique belongs to.
Overfitting & generalization
A model can memorize its training data and fail on anything new. Train/validation/test splits exist to catch this; regularization exists to prevent it. The tension between fitting the data and generalizing beyond it is the central drama of all machine learning.
Evaluation metrics
Accuracy lies when classes are imbalanced - a fraud model that says "not fraud" every time is 99.9% accurate and useless. Precision, recall, F1, and AUC each answer a different question. Choosing the right metric is a product decision disguised as a technical one.
Statistical intuition, minimum viable dose
Distributions, sampling, correlation vs causation, base rates, and why more data usually beats cleverer models. You don't need to derive anything - you need to stop being fooled by numbers, because the entire field reports itself in them.
Classical ML still runs the world
Linear and logistic regression, decision trees, random forests, gradient boosting (XGBoost). For tabular data - fraud scores, credit risk, churn - these still beat neural networks in most production systems, train in minutes, and are explainable to a regulator. Know when not to reach for deep learning.

phase two

Neural Networks & Deep Learning

The family of models that ate the field. What a neural network is, why depth was untrainable until it wasn't, and the architecture lineage - CNNs, RNNs - that explains why transformers were invented at all.

1–2 weeks · ~10 hours of material

When this is done: you can explain what a neural network computes (layers of weighted sums and activations), what backpropagation does, why GPUs and not algorithms unlocked deep learning, and what CNNs and RNNs were each good at and where each one hit a wall.

Concepts to own

Neurons, layers, activations
A "neuron" is a weighted sum passed through a simple nonlinear function (ReLU: negative becomes zero). Stack them in layers and the network can approximate almost any function. No biology required - it's arithmetic arranged in a particular shape.
Backpropagation
The algorithm that made deep networks trainable: efficiently compute how much each of millions of parameters contributed to the error, so every one can be nudged in a single pass. Conceptually it's the chain rule applied backwards through the network - you need the idea, not the derivation.
Optimizers, learning rates, batches
SGD and Adam decide how the nudging actually happens; the learning rate decides how big each nudge is; batching decides how many examples to average before nudging. These knobs are why "training" is a craft and why training runs fail.
The GPU revolution
Deep learning's breakthrough was less algorithmic than economic: graphics cards happened to be matrix-multiplication machines, and neural networks are mostly matrix multiplication. AlexNet (2012) on two gaming GPUs beat every hand-crafted vision system and the field pivoted overnight.
CNNs - convolutional networks
Vision's architecture: small filters slid across an image detect edges, then textures, then objects - hierarchy built in. The "inductive bias" idea matters beyond vision: bake what you know about the data's structure into the architecture and you need far less data.
RNNs, LSTMs, and the sequential wall
Recurrent networks read sequences step by step, carrying a running summary. LSTMs patched their memory problems, but the serial dependency remained: no parallelism within a sequence, degrading signal over distance. That wall is precisely what transformers were invented to break - understand it and the next phase is obvious rather than magical.
Embeddings, pre-LLM
word2vec (2013) showed that words could be placed in a vector space where meaning is geometry - king − man + woman ≈ queen. Every embedding model, vector database, and semantic search product descends from this idea. It predates transformers and explains them.

03
phase three

The Mental Model

The LLM landscape before touching a line of code. What an LLM is, what it isn't, and why this wave is different from every AI hype cycle before it.

2–3 days · ~5 hours of material

When this is done: you can explain what a language model actually does - next-token prediction at extraordinary scale - and describe the modern AI stack (foundation model → prompting → RAG → agents → product) to anyone.

Concepts to own

What an LLM actually is
A statistical next-token predictor trained on most of human text. Not a brain, not a database, not a search engine. Pattern completion at a scale where useful reasoning-like behaviour emerges.
The model landscape
Frontier closed models (GPT, Claude, Gemini) versus open-weight models (Llama, Mistral, Qwen, DeepSeek). Who builds them, how they're priced, and what the tradeoffs are for someone building a product. The open-closed capability gap is now measured in benchmark points, not generations - which changes the build-vs-buy math.
The AI stack
Foundation model → fine-tuning → prompting → retrieval (RAG) → agents → product. Each layer adds capability without retraining the base model. Almost every AI product is a composition of these layers.
Why now is different
Scaling laws, instruction tuning, and reinforcement learning from human feedback turned raw text completers into steerable, general-purpose engines. Tool use then turned them into things that can act.
The core vocabulary
Token, context window, parameters, inference, training, embedding, hallucination, temperature. Own these eight words before anything else - every other concept builds on them.

04
phase four

How LLMs Work

The internals: transformers, attention, tokens, context, the training pipeline - and the scaling laws that explain why any of it works. Deep enough to teach it, not to build one.

1–2 weeks · ~14 hours of material

When this is done: you can explain transformers, attention, tokenization, context windows, the full training pipeline (pretraining → instruction tuning → RLHF), and the scaling-law logic behind the entire industry - to a CEO or an engineer, at whichever depth they need.

Concepts to own

Tokenization
Text becomes tokens via byte-pair encoding. Roughly ¾ of a word per token in English, far worse in other languages. Tokenization explains cost, context limits, and many strange model failures (spelling, arithmetic, rare words).
Transformers & attention
The 2017 architecture behind everything. Self-attention lets every token weigh its relationship to every other token in parallel - a soft, learned lookup where queries match against keys and blend values. That mechanism made scale possible and killed recurrent networks.
Pretraining
Next-token prediction over trillions of tokens. This is where world knowledge gets compressed into weights. Compute plus data equals capability, with a predictability described by scaling laws.
The data pipeline behind pretraining
Web crawls filtered, deduplicated, quality-scored, and mixed with code, books, and synthetic data - data curation now moves capability as much as architecture does. "Trained on the internet" hides an enormous engineering discipline, and data quality disputes (and lawsuits) live exactly here.
Scaling laws & emergence - why this works
Kaplan (2020) then Chinchilla (2022): loss falls predictably as you scale parameters, data, and compute - predictably enough to justify billion-dollar training runs in advance. "Emergent" capabilities appearing at scale are real but contested; know both the claim and the critique, because vendors lean on the word.
Instruction tuning & RLHF
A pretrained model is a wild autocomplete. Supervised fine-tuning on instruction data makes it helpful; reinforcement learning from human feedback makes it steerable and safe. This combination was the ChatGPT breakthrough.
Reasoning models
Post-2024 models trained with reinforcement learning to produce long internal chains of thought before answering - trading inference-time compute for accuracy on hard problems. A second scaling axis (think longer, not just train bigger) that now shapes pricing, latency, and product design.
Context windows
The model's working memory: everything inside is visible, nothing outside exists. Modern windows run from 128K to over a million tokens, but retrieval quality degrades with position - "lost in the middle" is real. Attention cost also grows with the square of length: long context is never free.
Hallucination is structural
A next-token predictor optimized for plausibility will produce fluent falsehoods; there is no internal flag distinguishing knowledge from confabulation. It can be reduced (grounding, retrieval, abstention training) but not removed - which is why phases 10 and 11 exist.
Sampling: temperature, top-p
The model outputs a probability distribution over the next token; sampling settings decide how it picks. Temperature 0 for extraction and evals, ~0.7–1.0 for creative work. Knowing which knob to turn is a practitioner skill.

phase five

Choosing Models & the Open Ecosystem

There are thousands of models. Which one, hosted where, under what license, at what size? Model-selection literacy - reading model cards, decoding names, navigating Hugging Face - is a permanent working skill, not trivia.

1 week · ~6 hours plus a local install

When this is done: you can read any Hugging Face model page and know what you're looking at, explain open-weight vs open-source and why the license matters commercially, decode a model name like "Qwen3-30B-Instruct-AWQ" on sight, run a model locally, and walk through a defensible selection framework for any workload.

Concepts to own

Open weights ≠ open source
Open weights: the trained numbers are downloadable. Open source: weights plus training code, data recipe, and a genuinely permissive license. Most "open" models are the former. For a company, the difference lives in the license terms - commercial-use clauses, user caps, redistribution rules - and legal will ask.
License literacy
Apache 2.0 and MIT: do almost anything. Llama-style community licenses: permissive with conditions. Research-only licenses: no production, full stop. Checking the license is step one of model selection in any company, and skipping it is how prototypes become compliance incidents.
Decoding model names
"Qwen3-30B-Instruct-AWQ": family and generation, parameter count, post-training variant (base = raw predictor, instruct = chat-tuned), quantization format. Suffixes like GGUF, AWQ, GPTQ tell you how it's compressed and what runs it. Thirty seconds of literacy that filters ninety percent of confusion.
Model cards & system cards
The model card is the datasheet: intended use, training data notes, eval results, limitations, license. Frontier labs publish system cards covering safety testing. Reading these critically - especially what's not reported - is the difference between selecting and guessing.
The Hugging Face ecosystem
The Hub (models, datasets, spaces), the transformers library, and the conventions that make "download and run any model in ten lines" work. It's the GitHub of machine learning; fluency here is fluency in the open ecosystem itself.
The model families map
Frontier closed (GPT, Claude, Gemini) · open heavyweights (Llama, DeepSeek, Qwen, Mistral) · small-and-efficient (Phi, Gemma, Haiku-class) · specialists (code, embeddings, rerankers, vision, speech). Hold the map loosely - names churn quarterly, the categories don't.
The selection framework
In order: does it meet the capability bar on your eval (never the vendor's), does it meet latency, what does it cost at your volume, does the license permit your use, and can you host it where your data is allowed to live. Five questions, asked in that order, every time.
Run one locally, today
Install Ollama or LM Studio, pull a small instruct model, and talk to it. Feeling a 4B model's strengths and failures firsthand recalibrates every claim you'll ever read about model capability - and it takes fifteen minutes.

phase six

Prompting & Context Engineering

Your primary interface with every model, forever. Most people never actually master this - which is exactly why it's a differentiator.

1–2 weeks · ~8 hours of material plus practice

When this is done: you can reliably extract structured, predictable output from any LLM using system prompts, few-shot examples, and chain-of-thought - and you can call any model API with confidence.

Concepts to own

System prompts
The instruction frame that governs model behaviour: persona, constraints, output format, tone, refusal rules. Most AI products live or die on the quality of this one document.
Zero-shot vs few-shot
Zero-shot: just ask. Few-shot: show examples first. Few-shot is dramatically more reliable for structured or stylistically-precise output, at the cost of tokens.
Chain-of-thought
Asking the model to reason step by step measurably reduces errors on complex tasks. Reasoning models now bake this in with dedicated thinking tokens - know when you're paying for thinking you don't need.
Structured output & function calling
JSON mode, schemas, and function calling force the model to return parseable data instead of prose. This is the foundation of every product integration - and of agents, two phases from now.
Context engineering
The term that replaced "prompt engineering": deciding what goes into the context window, in what order, and why. Instructions, examples, retrieved documents, tool results, history - composition is the skill.
API mechanics
Messages arrays (system / user / assistant turns), max tokens, stop sequences, streaming, rate limits, prompt caching, and cost per token. Know these before building anything.

phase seven

Embeddings, Vectors & RAG

How AI systems gain knowledge beyond their training data. Retrieval-augmented generation is still the dominant production pattern for knowledge-intensive products.

1–2 weeks · ~10 hours of material plus one build

When this is done: you can design and build a working RAG pipeline end-to-end, explain why each stage exists, diagnose where retrieval quality breaks, and evaluate the whole thing with real metrics.

Concepts to own

Embeddings
Dense vectors that represent meaning. "Cat" and "feline" land close together in embedding space; "cat" and "democracy" don't. This is how machines do semantic similarity - the foundation of search, recommendations, clustering, and RAG. (You met the ancestor, word2vec, in phase 02.)
Vector databases
Databases optimised for approximate nearest-neighbour search in high-dimensional space: Pinecone, Weaviate, Qdrant, Chroma, pgvector, and vector features inside every major cloud DB. Know two well; know when plain Postgres with pgvector is enough (often).
The RAG pipeline
Ingest → chunk → embed → store → (query → embed → retrieve → rerank) → inject into context → generate with citations. Every stage has failure modes; being able to name them is what separates practitioners from tourists.
Chunking strategies
How you split documents affects retrieval quality more than almost anything else. Fixed-size, recursive, semantic, and document-structure-aware chunking each have a use case. Bad chunking cannot be fixed downstream.
Hybrid search & reranking
Dense (semantic) plus sparse (keyword/BM25) search almost always beats either alone. A cross-encoder reranker on top of retrieval is the cheapest big precision win available.
Knowledge graphs & GraphRAG
When answers require connecting entities across documents ("which vendors touch systems affected by this regulation?"), vector similarity alone underperforms. GraphRAG extracts an entity-relationship graph at ingestion and traverses it at query time. Heavier to build, dramatically better for relational questions - know when the question shape demands it.
Evaluating RAG
Faithfulness, answer relevancy, context precision, context recall - the RAGAS framework's four dials. If you can't measure retrieval quality, you can't improve it.
When not to RAG
Long context windows, prompt caching, and agentic search have eaten some of RAG's territory. Knowing when to just stuff documents into context - or let an agent search - is a current, live product judgment.

08
phase eight

Agents, Harnesses & Loop Engineering

The single most important idea in applied AI right now: a model, given tools and a loop, becomes a system that can act. Everything currently being built lives here.

2 weeks · ~10 hours of material plus one build

When this is done: you can explain exactly what an agent is (LLM + tools + loop), trace an agent's reasoning cycle step by step, name the major failure modes, and build a simple tool-using agent without a framework.

Concepts to own

The agent loop
Reason → choose a tool → act → observe the result → reason again, until done or stuck. That loop, popularised by the ReAct paper, is the whole trick. Every agent framework is scaffolding around this cycle.
Tool use / function calling
The model emits a structured call (search the web, query a database, run code, send an email); the host executes it and feeds the result back into context. Tools are how a text predictor gets hands.
Workflows vs agents
A workflow is a predefined chain of LLM calls; an agent decides its own path at runtime. Workflows are cheaper, more reliable, and right for most products. Knowing when you actually need agency is a core product judgment.
Agent memory
Four kinds: in-context (the conversation), external (a vector store), episodic (summaries of past sessions), and procedural (learned routines). Long-running agents live or die on memory design.
Planning & decomposition
Good agents break big goals into steps, track progress, and recover from failures. Techniques: explicit plan-then-execute, todo lists in context, reflection steps, and human checkpoints at irreversible actions.
Harness engineering
The harness is everything around the model: tool definitions, context assembly, output validation, verifiers, retry policy, stop conditions, checkpoints. Coding agents proved the thesis - a smaller model in a great harness beats a frontier model in a bad one - because the harness supplies the feedback loop the model lacks.
Loop engineering & budgets
Designing the iteration itself: maximum steps, token and cost ceilings, progress detection (is the agent advancing or thrashing?), checkpointing state so failures resume instead of restart, and explicit exit criteria. An unbudgeted loop is an outage with extra steps.
Sandboxing & blast radius
Agents that execute code or touch production systems run in sandboxes with least-privilege credentials, allowlisted actions, and human gates at irreversible steps. Design the blast radius before the capability - especially anywhere money moves.
Agent failure modes
Infinite loops, hallucinated tool parameters, goal drift, context overflow, cascading errors, and prompt injection through tool results. Phase 10 turns these into an engineering discipline.
Agentic RAG & computer use
Instead of one-shot retrieval, the agent decides when to search, reformulates queries, evaluates results, and searches again. Computer-use agents extend the same loop to screens and browsers - the current frontier of "tools."

phase nine

MCP, Graphs & Multi-Agent Systems

The infrastructure layer of the agentic era: standard protocols for connecting agents to tools, and patterns for making multiple agents work together.

1–2 weeks · ~8 hours of material

When this is done: you can explain MCP and A2A and why standard protocols matter, build or spec an MCP server, and reason about multi-agent architectures - orchestrator-worker, sequential, hierarchical - like a systems designer.

Concepts to own

MCP - Model Context Protocol
An open standard (originated by Anthropic, now industry-wide) for connecting AI applications to tools and data sources. Think USB-C for AI: any client, any server, one protocol. Its primitives - tools, resources, prompts - are worth knowing cold.
Why protocols beat integrations
Before MCP: N models × M tools = N×M custom integrations. After: N + M. This is the same story as HTTP, SQL, and REST - and understanding it lets you predict where the ecosystem is heading.
A2A - Agent-to-Agent protocol
Google-originated, Linux Foundation-governed standard for agents discovering and talking to each other. MCP connects agents to tools; A2A connects agents to agents. Together they're the emerging agentic stack.
Multi-agent patterns
Sequential (pipeline of specialists), orchestrator-worker (a lead agent delegates to subagents), hierarchical (managers of managers), and debate/critique loops. More agents means more capability and much more failure surface - most products need fewer agents than founders think.
Graph thinking & state machines
Serious agent systems are graphs: nodes are steps (model calls, tools, human gates), edges are transitions, and state flows through explicitly. This is why LangGraph won the production niche - graphs make loops, branches, retries, and resumability inspectable instead of implicit. If you can draw the state machine, you understand the system.
Orchestration frameworks
LangGraph (stateful graphs, production-leaning), CrewAI (role-based teams, fast to prototype), AutoGen/Agent Framework (Microsoft, conversation-driven), smolagents (Hugging Face, minimal, code-first). Learn one deeply - LangGraph is the safest deep bet - and stay conversant in the rest.
Agent observability
Tracing every step - which tool was called, with what input, what came back, what it cost - via LangSmith, Langfuse, or similar. Debugging a multi-agent system without traces is archaeology.

phase ten

Reliability Engineering

Building dependable systems out of a probabilistic component. Structured outputs, validation, retries, fallbacks, guardrails, and the compounding-error math that decides whether your agent survives production.

1–2 weeks · ~8 hours of material plus one build

When this is done: you can design a pipeline where every model output is validated before it's trusted, explain why a 95%-per-step agent fails at ten steps (0.95¹⁰ ≈ 0.60), and draw the standard reliability stack - schema validation → retries → fallbacks → guardrails → human checkpoints - from memory.

Concepts to own

Compounding error - the core math
Per-step accuracy multiplies across sequential steps: 95% per step is 60% at ten steps and 36% at twenty. This single equation explains why agent demos work and agent products fail, why verifiers matter more than bigger models, and why every serious harness caps loop length.
Validate everything, trust nothing
Every model output gets checked before use: JSON schema validation (Pydantic, Zod), business-rule checks, and type coercion. Libraries like Instructor make "the model returns a typed object or the call retries" the default pattern rather than an aspiration.
Retries, fallbacks & graceful degradation
Failed validation → retry with the error in context. Still failing → fall back to a stronger model, a simpler prompt, or a deterministic path. Never let a raw failure reach the user; always know what the system does when the model is wrong, slow, or down.
Self-verification & LLM-as-judge in the loop
Cheap model generates, stronger model verifies - or the same model critiques its own draft before finalizing. Verification is dramatically easier than generation, which is why judge-in-the-loop beats simply buying a bigger generator.
Guardrails frameworks
Programmable input/output rails: topic restrictions, PII filters, jailbreak detection, tool-permission boundaries. NeMo Guardrails and Llama Guard are the reference implementations; the concept - a policy layer outside the model - matters more than any specific tool.
Model routing & tiering
Classify the request, route easy ones to cheap fast models and hard ones to frontier models, escalate on failure. The single highest-leverage cost-reliability tradeoff in production systems - and the architecture pattern behind every serious AI platform.
Deterministic core, probabilistic shell
Anything with an exact right answer - parsing a payment message, computing a checksum, validating an ID - is code, never a model. The model routes, judges, and explains; deterministic tools execute. In regulated domains this split is the difference between a product and an incident.

phase eleven

Evals, Safety & Compliance

The discipline that separates serious AI teams from the rest - and, in regulated industries, the difference between shipping and being shut down. Measurement, adversarial thinking, and the regulatory landscape.

2 weeks · ~10 hours of material plus one eval suite built

When this is done: you can build an eval suite from scratch (golden set, LLM-as-judge, regression on every change), explain prompt injection and why it's unsolved, run a basic red-team exercise, and speak fluently about the EU AI Act, PII handling, and audit requirements in a client conversation.

Concepts to own

Evals - the number one skill
LLM output is probabilistic, so quality must be measured systematically: golden datasets, LLM-as-judge, human review loops, regression suites on every prompt change. "It feels good" is not an eval. Teams that master evals ship faster and safer than teams that don't.
Benchmark literacy
MMLU, GPQA, SWE-bench, LMArena - know what each measures, who runs it, and why to be sceptical of every vendor-reported number. Independent leaderboards over press releases, always. Public benchmarks also leak into training data; your private eval set is the only one you can fully trust.
Prompt injection - the unsolved problem
Any text your system ingests - documents, emails, web pages, tool results - can contain instructions that hijack the model. There is no reliable fix; defense is layered: input isolation, least-privilege tools, output validation, and human checkpoints on consequential actions. If your agent reads untrusted text and can take actions, you have this problem.
Red-teaming & jailbreak awareness
Systematically attacking your own system before someone else does: role-play exploits, encoding tricks, multi-turn manipulation, data-extraction probes. In a bank, this is not optional - it's the security review.
PII, data residency & audit trails
What data leaves your infrastructure, where it's processed, how long the vendor retains it, and whether you can produce a complete trace of every model decision for an auditor. These questions decide procurement in finance - know the answers for every architecture you propose.
The regulatory landscape
The EU AI Act's risk tiers (credit scoring is high-risk; obligations follow), NIST's AI Risk Management Framework as the de-facto vocabulary, and sector regulators - central banks included - converging on explainability, human oversight, and model documentation. Regulation is a product constraint, not a legal footnote.
Alignment & safety basics
Why models refuse, how RLHF and constitutional approaches shape behaviour, and the gap between "aligned in the lab" and "safe in your product." You own the second one; the vendor owns the first.

phase twelve

Inference Economics & Infra

Where the money goes. GPUs, memory bandwidth, quantization, serving stacks, and the cost arithmetic that decides API-vs-self-host - the layer that makes "cheap, scalable AI" a real claim instead of a slide.

1–2 weeks · ~8 hours of material

When this is done: you can explain why inference is memory-bound, what quantization and KV caching actually save, how vLLM-style serving multiplies throughput, and build a defensible cost model comparing frontier APIs against self-hosted open models for a given workload.

Concepts to own

Why inference is memory-bound
Generating each token requires reading every parameter from GPU memory. A 70B model in 16-bit is 140GB of weights read per token - memory bandwidth, not raw compute, sets the speed limit. This one fact explains most of inference optimization.
Prefill vs decode
Processing the prompt (prefill) is parallel and compute-bound; generating tokens (decode) is sequential and memory-bound. Time-to-first-token and tokens-per-second are different problems with different fixes - and different line items in your latency budget.
KV cache
Attention over previous tokens is cached rather than recomputed, trading memory for speed. Cache size grows with context length and batch size - it's why long contexts eat GPU memory, why prompt caching is priced separately, and where much of serving innovation happens.
Quantization
Storing weights in 8-bit or 4-bit instead of 16-bit halves or quarters memory needs with modest quality loss - the reason a 70B model fits on one GPU at all. GPTQ, AWQ, and GGUF are the formats you'll meet; know what tradeoff each represents.
Serving stacks & continuous batching
vLLM, SGLang, TensorRT-LLM: engines that batch many users' requests dynamically onto one GPU, multiplying throughput 5–20× over naive serving. If you self-host without one of these, you're setting money on fire.
Distillation & small-model economics
Training a small model to imitate a large one on a narrow task - how 7B–30B models get frontier-adequate at specific jobs. Combined with routing (phase 10), this is the core mechanism behind every "10× cheaper" claim worth believing.
The build-vs-buy cost model
API cost = tokens × price, scales to zero. Self-host cost = GPUs × hours + engineering + reliability risk, scales with peak capacity. Break-even depends on utilization, and most teams overestimate theirs. Being the person who can run this math honestly is a career skill.
GPU landscape literacy
H100/B200 class for training and heavy serving, L40S/A10 class for light inference, consumer cards for local prototyping - plus the accelerator alternatives (TPU, Trainium, Groq-style ASICs). Know the tiers and rough rental prices; ignore the model numbers racing past.

phase thirteen

AI Product Craft

Where engineering stops and product thinking starts: product patterns, trust design, unit economics, and the judgment calls that make AI features shippable.

2–4 weeks · ongoing practice

When this is done: you can spec, evaluate, and ship AI products. You know how to design for probabilistic failure, manage cost and latency as product constraints, choose the right pattern for the problem, and speak fluently to engineers and executives alike.

Concepts to own

The AI product patterns
Chatbot, copilot, autonomous agent, background workflow, and multimodal app. Every AI product is one of these or a combination - and each has distinct UX, trust, and reliability requirements.
Hallucination as a product problem
Grounding, citations, constrained output, confidence signals, and human-in-the-loop are product strategies, not just model fixes. The right answer depends on the cost of being wrong in your domain.
Trust & failure UX
Show sources, show uncertainty, make undo cheap, and put humans at irreversible steps. Users forgive a system that fails visibly and recovers gracefully; they abandon one that fails confidently.
Cost & latency as product constraints
Model tiers differ in price by 20–100×. Prompt caching, streaming, batch endpoints, and routing cheap requests to small models are PM-level decisions that make or break unit economics. (Phase 12 gave you the math; here you apply it to a roadmap.)
Build vs buy vs prompt vs fine-tune
The canonical decision ladder: try prompting first, then RAG, then fine-tuning, then custom models - escalating only when the previous rung measurably fails. Most production problems die on rung one or two.
Speaking both languages
Translating "the eval regression on the golden set" upward into risk and revenue, and "make it feel smarter" downward into measurable spec. This translation is the actual job of an AI PM, and it's rarer than either skill alone.

phase fifteen

Fine-tuning, Frontier & Staying Sharp

The last technical layer - when prompting and RAG aren't enough - plus the multimodal frontier and the permanent learning system, because this field reinvents itself every few months.

1–2 months, then forever

When this is done: you know when fine-tuning is justified and how it works (LoRA, QLoRA, preference optimisation), you hold a working map of the multimodal and reasoning frontier, you can evaluate any new model or tool within thirty minutes, and you have a weekly system for tracking the field.

Concepts to own

When to fine-tune
When you need a style or format prompting can't reliably produce, have at least ~1,000 high-quality examples, or need a small cheap model to match a big one on a narrow task. Fine-tuning teaches behaviour, not facts - facts belong in retrieval. It's the last resort on the decision ladder, not the first move.
LoRA & QLoRA
Parameter-efficient fine-tuning: train a small adapter instead of all the weights. QLoRA adds quantisation so large models can be tuned on a single GPU. This is how almost all practical fine-tuning happens - and note what it can't do: the tokenizer stays frozen, so domain jargon still fragments the same way.
Preference optimisation & RL
RLHF, DPO, and GRPO - how models are aligned to human preferences and trained to reason. Understanding these at a conceptual level lets you read any model release announcement critically.
Domain vocabulary extension
The rare, heavy technique that actually fixes jargon tokenization: add domain tokens, initialize their embeddings, continue pretraining. Used by legal and medical model variants. Know it exists, know it's a pretraining-scale project, and know when volume justifies it.
Fine-tuning locally, in practice
The actual workflow: pick a small open model, format your examples (instruction/response pairs), train a QLoRA adapter with Unsloth or Axolotl on a single GPU or Colab, evaluate against the base model, and merge or serve the adapter. Doing this once end-to-end - even on a toy dataset - converts fine-tuning from a buzzword into a tool you can scope.
Synthetic data & distillation pipelines
Using a strong model to generate or label training examples for a smaller one - now the dominant way fine-tuning datasets get built. Quality control on synthetic data (dedup, filtering, judge-scoring) matters more than volume, and license terms on generated outputs matter commercially.
Multimodal & beyond text
Vision-language models, speech-native models, image and video generation, and computer-use agents. The product frontier is multimodal; keep a working mental map even if you build with text first.
The 30-minute model eval
New model drops: read the system card, check independent benchmarks, run your own hardest prompts, check pricing, read two practitioner takes. You can have a defensible opinion in half an hour - this is the skill that keeps you current forever.

Glossary · Pin this
Model
An architecture (a shape with blanks) plus parameters (the trained numbers filling them).
Parameters / weights
The adjustable numbers set by training. "70B" means seventy billion of them.
Loss function
The score of how wrong a prediction was - the thing training minimizes.
Gradient descent
Guess, measure error, nudge every parameter to be slightly less wrong, repeat millions of times.
Overfitting
Memorizing training data instead of learning patterns that generalize to new data.
Inference
Running a trained model on new input. Training sets the knobs; inference uses them.
Token
The unit of text a model reads and writes - roughly ¾ of an English word.
Context window
The model's working memory. Inside is visible; outside doesn't exist.
Embedding
A vector of numbers representing meaning; similar meanings sit close together.
Vector database
A store optimised for finding the nearest vectors - i.e. searching by meaning.
RAG
Retrieve relevant documents at query time and hand them to the model, instead of retraining it.
Agent
A model with tools and a loop: reason, act, observe, repeat until done.
Tool / function calling
The model emits a structured request; your code executes it and returns the result.
MCP
Open protocol connecting AI apps to tools and data. USB-C for AI.
A2A
Open protocol for agents to discover and communicate with other agents.
Fine-tuning
Continuing a model's training on your own examples to change its behaviour - not its facts.
LoRA
Fine-tuning via a small trained adapter instead of all the weights. Cheap and standard.
Transformer
The neural architecture behind every modern LLM, built on attention.
Attention
The mechanism letting each token weigh its relationship to every other token.
Scaling laws
The predictable relationship between compute, data, parameters, and capability.
RLHF
Reinforcement learning from human feedback - how raw predictors become steerable assistants.
Reasoning model
A model trained to think in long internal chains before answering - accuracy bought with inference time.
Hallucination
Fluent, confident output that is simply wrong. Structural, reducible, not removable.
Eval
A systematic measure of output quality. The discipline separating serious AI teams from the rest.
Prompt injection
Hostile instructions hidden in ingested text that hijack the model. Unsolved; defend in layers.
Guardrails
A policy layer outside the model: input filters, output validation, tool permissions.
Quantization
Storing weights in fewer bits (8, 4) to cut memory and cost with modest quality loss.
KV cache
Cached attention state that makes generation fast - and makes long contexts eat GPU memory.
Distillation
Training a small model to imitate a large one on a narrow task. The engine of cheap inference.
Harness
Everything around the model: tools, validation, verifiers, retries, stop conditions. Where reliability lives.
Loop budget
Hard ceilings on an agent's steps, tokens, and cost. An unbudgeted loop is an outage.
Open weights
Downloadable trained parameters. Not the same as open source - the license decides what you may do.
Model card
A model's datasheet: intended use, evals, limitations, license. Read what it omits, too.
GraphRAG
Retrieval over an extracted entity-relationship graph - for questions that connect things.
Synthetic data
Training examples generated by a stronger model. How most fine-tuning datasets get built now.
Model routing
Sending easy requests to cheap models and hard ones to frontier models. The core cost lever.
